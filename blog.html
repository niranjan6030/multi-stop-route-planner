Many places to go, which one first? How I built a multi-stop route planner

Niranjan S  |  BCA, CHRIST (Deemed to be University), Bengaluru  |  October 2026

For my routing assignment I wanted to make something that a normal person could actually use, not only a demo of an algorithm. So I picked a problem that almost everyone has had: you have a list of places to go to in one trip, and you do not know in which order to visit them.

This post explains the problem, the algorithm I used, how I tested it and how fast it is. You can try the working prototype here: open the route planner.

1. The problem

Think of a delivery boy with 12 parcels, a shop owner who drops orders at customers' houses, or a family going around the city giving wedding invitations. Google Maps is very good at showing the way from A to B. But when there are many stops, the order of the stops is left to you, and a bad order means a lot of extra kilometres, petrol and time.

Here is an example from my prototype. These are the same 9 places in Bengaluru. On the left I visit them in the order I typed them. On the right is the order my planner found.

That is 37.5 km saved (48%) without leaving out any place.

In computer science this is called the Travelling Salesman Problem (TSP): given a starting place and n stops, find the order that visits every stop once and comes back to the start with the smallest total distance.

Inputs and outputs

Input
  • The starting place and the stops. Each one has a name, latitude and longitude. The user searches for a place or clicks on the map.
  • Round trip (come back to the start) or one way.
  • A distance table D where D[i][j] is the km from place i to place j. The planner gets real road distances from OpenStreetMap (through the OSRM server) in one request. If there is no internet it uses straight line distance (haversine formula).
Output
  • The order to visit the stops.
  • Total km and driving time, and the km and minutes of every leg.
  • How many km are saved compared to the order the user typed.
  • The route drawn on the map, and a button that opens it in Google Maps.

Why is it hard?

The obvious idea is to try every possible order and keep the shortest. The trouble is that n stops can be visited in n! (n factorial) different orders.

Ten stops are still fine for a computer. Twenty stops are not, as I measured later.

2. The algorithm

I use two simple methods one after the other, and an exact check when the list is small. All of it is in one file, js/tsp.js, about 200 lines of plain JavaScript. Place 0 is always the start.

Step 1: Nearest neighbour (build a first route)

Start at home. Always go to the closest place that is not visited yet. That is all.

function nearestNeighbour(D) {
  var n = D.length;
  var visited = [];
  for (var i = 0; i < n; i++) visited.push(false);

  var route = [0];
  visited[0] = true;
  var at = 0;

  for (var step = 1; step < n; step++) {
    var next = -1;
    for (var j = 0; j < n; j++) {
      if (!visited[j] && (next === -1 || D[at][j] < D[at][next])) next = j;
    }
    visited[next] = true;
    route.push(next);
    at = next;
  }
  return route;
}

It is very fast, but it does not look ahead. It keeps taking the easy nearby places, and at the end the last places are far away. The route often crosses over itself.

Step 2: 2-opt (improve the route)

2-opt takes a route and tries to make it better. It picks two links of the route, removes them and joins the route the other way, which reverses the part in between. If the route is shorter now, the change is kept. It repeats this for every pair of links until one full pass finds nothing to improve.

The nice thing is that reversing a part only changes two links, so I do not have to add up the whole route again. If a-b and c-d are the two links, I only check this:

change = D[a][c] + D[b][d] - D[a][b] - D[c][d];
if (change < 0) {
  // reverse the part of the route between b and c
}

A small example

Six places on a km grid, H is home. Nearest neighbour gives the route on the left. You can see the two red links crossing. 2-opt removes them and adds the two blue ones.

The removed links D-A and C-B are 2.24 + 7.81 = 10.05 km. The new links D-C and A-B are 3.16 + 4.24 = 7.40 km. So the route became 2.64 km shorter. I also tried all 5! = 120 orders for this example, and 18.73 km really is the best possible.

Step 3: exact search, only for 10 stops or fewer

When the list is small, trying every order is affordable, so the planner does it and gives the guaranteed best answer. I made it faster with pruning: the search builds a route one place at a time, and if the half built route is already longer than the best complete route found so far, it stops and goes back, because it can never win. The 2-opt route is given to it as the first "best", so most orders are thrown away early.

var len = lengthSoFar + D[last][next];
if (prune && len >= bestLength) continue;     // already too long, skip this branch

For the 9 places in the picture above (8 stops, 40,320 possible orders) the search had to finish only 102 complete routes to be sure of the answer.

3. The prototype

The prototype is a web page made with HTML, plain JavaScript, Bootstrap and the Leaflet map library. There is nothing to install and it works on a phone. Open it here and press "Load an example" if you just want to see it work.

  • Add places by searching or by clicking on the map. The first place is the start.
  • Real road distances from OpenStreetMap, straight line distance when offline.
  • Round trip or one way.
  • Shows the km saved, and the km and minutes of every leg.
  • A link switches the map between "my order" (red) and "shortest order" (blue).
  • A button opens the final order in Google Maps so you can start driving.

One small detail: road distance from A to B is not exactly the same as from B to A because of one-way streets. 2-opt reverses parts of the route, so it needs both directions to be equal. I take the average of the two before running the algorithm, and at the end I check both directions of the round trip with the real distances and show the shorter one.

5. Why this algorithm?

I compared the methods I could have used. The numbers in the last column are from my own experiments (next section).

MethodBest route?TimeWhat I found
Try every order (brute force)YesO(n!)149 ms at 10 stops. At that rate 15 stops would need about 15 hours.
Every order + pruningYesO(n!) worst case16 times faster at 10 stops (9 ms), but 154 ms at 12 and growing fast.
Held-Karp (dynamic programming)YesO(n² 2n)Needs O(n 2n) memory and is harder to write. I did not try it.
Nearest neighbour onlyNoO(n²)Instant, but about 14% longer than the best route.
Nearest neighbour + 2-optAlmostO(n²) per passAbout 1% longer than the best, in under 0.001 ms.

So the planner uses the exact search when that is cheap (10 stops or fewer, under 10 ms) and nearest neighbour + 2-opt when it is not. For a person driving around a city, a route that is 1% longer than perfect and comes instantly is much more useful than a perfect one that takes hours.

Why not Dijkstra or A*? I get asked this because those are the famous routing algorithms. They solve a different problem: the shortest path between two places. That part is already done by the OSRM server when it gives me the road distance of each pair. Dijkstra cannot decide the order of the stops, which is the actual problem here.

6. Time and space complexity

PartTimeExtra space
Distance tableO(n²)O(n²)
Nearest neighbourO(n²)O(n) for the visited list
2-optO(n²) per pass, p passesO(n) for a copy of the route
Exact search with pruningO(n!) in the worst caseO(n) recursion depth
Planner with more than 10 stopsO(p · n²)O(n²)

Here n is the number of places and p is the number of 2-opt passes. Nearest neighbour has two loops inside each other, so n². One 2-opt pass looks at every pair of positions, so also n². Nobody can say exactly how many passes 2-opt needs, but in my runs it was only 3 to 6, even for 800 stops.

8. What it cannot do, and what next

  • There is no live traffic. The driving time is what OSRM gives for empty roads.
  • Above 10 stops the route is very good but not guaranteed to be the best one.
  • It plans for one vehicle and does not know shop timings.
  • The free map servers are meant for light use, so I limited it to 25 places.

Next I want to add opening times for the places ("the bank closes at 4") and one more improvement move called or-opt, which moves a single stop to a better position.

What I learned

Before this project I thought a routing problem always means Dijkstra. The biggest thing I learned is that choosing the order of stops is a completely different and much harder problem, and that a simple method that is "almost best" can be the right choice when the perfect answer is too slow.
